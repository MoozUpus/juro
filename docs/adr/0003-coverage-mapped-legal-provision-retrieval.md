# Retrieve legal evidence as a coverage-mapped provision set

Source identity and eligibility now follow
[ADR 0005](./0005-use-source-snapshot-retrieval-eligibility.md). Any authority
metadata mentioned here is optional explicitly evidenced reranking enrichment,
not a Retrieval Eligibility gate, and must never be inferred.

For a natural-language legal question, JURO derives explicit Coverage Requirements for every materially plausible interpretation, generates candidates from versioned provision-aware sparse and dense indexes, and requires a semantic reranker to select the Provision Set that satisfies those requirements. Official Coverage is evaluated over that set, with one bounded targeted repair search for uncovered requirements; only an explicit, unambiguous act-and-article lookup may bypass semantic reranking.

A candidate's association with the Retrieval Formulation that found it is search provenance, not Requirement Support. Requirement Support is established only after the candidate's validated provision content has been assessed against the specific Coverage Requirement; ranking metadata alone cannot satisfy coverage.

## Consequences

Fast and deep answer modes share the same retrieval and evidence-safety contract. Natural-language retrieval requires both sparse and dense candidate channels before indexed Official Coverage can be good. Dense index representations include the act title, article number and title, hierarchy, language, and provision text; chunks remain grouped by provision through selection and hydration. The mandatory selector combines an independently versioned in-process ranking policy with one bounded, low-reasoning Requirement Support assessment over hash-verified provision text. The verifier receives neither retrieval tags nor previous assistant answers as evidence, receives one attempt, and may add a candidate-grounded Coverage Requirement that triggers the repair pass when unsupported. The Provision Set has no fixed top-result truncation: it contains sufficient evidence for every Coverage Requirement, and exceeding a bounded context ceiling produces a focused clarification or Insufficient-Evidence Result instead of silent omission. Only good-coverage packets may be cached, and their keys include corpus, index, reranker, and retrieval-policy versions so a stale or degraded selection cannot survive a rollout. Sparse and dense indexes are activated together through one versioned release manifest after local-app validation, while the previous pair remains available for immediate rollback. The Indexed Official Corpus stage, including selection and the optional repair pass, must satisfy the existing p95 five-second release gate rather than trading away coverage for speed.

The pinned staging or active promoted manifest remains immutable when its ephemeral Qdrant collection is lost. Deterministic point identities allow a finalized build to be reconciled back into a compatible empty collection without changing the release identity, and the corpus schedule touches that configured collection often enough to prevent routine scale-to-zero loss—even while a staging candidate has no activation row because a release gate remains open. Each scheduled touch also compares the collection's exact point count with the frozen manifest, because a compatible empty disk must not pass as healthy. Reconciliation serializes and paces embedding batches so recovery cannot burst through the provider guardrail and disable interactive legal requests. A missing, incomplete, or incompatible collection is Source Unavailability during recovery; it is never treated as absent legal coverage.
